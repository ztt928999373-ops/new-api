## 2. V1｜可靠文本 API 网关（当前唯一执行主线）

**目标用户**：首先验证个人开发者和小团队，不同时追求全部普通消费者与企业场景。

**核心价值**：
1. 统一文本 API 接口及可审计的模型/渠道选择；保留已有故障切换。
2. 安全 BYOK 和/或供应商明确授权的接入；凭据加密、撤销及最小权限。
3. 可核对的 Token、客户扣费、供应商成本、预算与冻结信息；不能核实时显示未知或限制请求，不虚构利润。
4. 可靠的封闭部署、备份/恢复、健康监控和告警；先以合成数据验收。

**执行批次，必须顺序过门**：

- **V1-G0 / D3 收尾**：先核对 `product/v1` 最新 SHA 对应的必需 CI；另经所有者批准才运行 D3 `full`。验收环境限额、固定 Digest、卷内权限、冷备份、全新卷恢复、重启持久化、配对回滚、清理及脱敏 Artifact。必须有真实 `d3_pass` 及 13 阶段全部成功，不能将 `preflight_pass` 视作完整验收。失败保留证据，独立最小修复 PR。
- **V1-G1 / 核心回归和缺口复盘**：先审查当前已合并的 #20/#21/#22/#28，避免重复修复旧报告中的 P1；运行最新版前后端、权限、凭据、费用/路由、安全与三数据库 CI；复核浏览器核心路径、审计和 Secret 不泄漏。旧 Draft #1/#19 只读对照，确认保留/关闭建议，不直接合并。缺口按 P0/P1/P2 标注负责人、复现、测试与证据。
- **V1-G2 / 真实供应商低风险小额验收**：经单独批准且核实供应商条款/地区/费用/授权后，选择一个文本上游、一个模型和明确额度上限；逐项检查 streaming/非 streaming、usage、失败/超时退款、权限、成本/价格来源与可追溯性。采购或实际调用不由本路线图授权。若真实账单无法确认，维持 Mock 和禁用渠道，不放行商业流量。
- **V1-G3 / 运营与试点门槛**：明确 BYOK 与收费转售的责任边界、许可证/署名/源码义务、数据处理与适用合规；付费功能仅在独立批准的沙箱验证订单、Webhook 幂等、退款/撤销及账务；完成 TLS、备份恢复、监控、额度限制及支持流程后才进入小规模封闭试运营。实际收款、部署和公开注册仍须另批。

**V1 释放条件**：参见 [V1 验收与放行清单](./v1-release-gates.md)。每项为 `PASS / FAIL / SKIPPED / NOT_RUN / UNKNOWN`，缺证据不能写 PASS。不得以总体通过率替代 P0 项目。

## 3. V1.5｜可衡量的智能路由（V1 门槛后启动）

**前提**：先拿到合法且可比的成本、延迟、错误率数据；保留 V1 的稳定固定优先级路由作为对照和回退。没有充分数据时不声称已有智能路由收益。

最小实现顺序：
1. **观测**：按匿名渠道/模型/时间桶采集成功率、端到端及首 Token 延迟分位数、估算/核实费用、超时、降级和熔断；不得记录提示词、真实密钥、用户敏感请求内容。保留样本量、数据新鲜度和缺失状态。
2. **候选过滤**：先按授权、模型能力、上下文/接口兼容性、渠道启用、预算/冻结、地区/隐私约束、健康与可用配额进行硬过滤；不符合的渠道不得因低价被选中。
3. **影子策略**：复用当前固定优先级作为 baseline，离线/影子评估最小成本、最低延迟、成本-成功率加权等策略，不发送重复付费请求。保存原因码和路由决策，可回放。
4. **小流量灰度**：只有在样本和回滚策略充足、经审批后才开启；测量相对 baseline 的请求成功率、p95 时延、每次成功请求上游成本、超预算和故障率，任何安全/成本硬门槛失守自动回退。
5. **效果报告**：输出按模型/渠道/时间窗口分组的效果与置信界限。质量评价以明确任务集或真实授权反馈为依据，不假设更便宜/更快就一定更好。

**V1.5 完成定义**：策略可解释、可禁用、可回滚；对至少一个真实且受控场景证明非劣于固定优先级的成功率与预算安全，并在时延或成本至少一项上有可复核改善。具体阈值在基线数据形成后批准，不编造现在的达标率。

## 4. V2｜多模态与小团队能力（按验证需求排序）

基于同一网关增加能力，不同时启动三个独立平台：
1. **V2-A 图像**：先统一模型目录能力标签、请求格式、价格维度、限流和安全规则；支持生成/编辑时区分计费单位、文件保留策略与敏感内容。
2. **V2-B 视频与长任务**：仅在图像/基础网关成熟后增加异步任务、状态轮询/Webhook、超时/取消、成本预留与核销、对象存储生命周期和失败恢复。视频不能沿用纯文本 Token 计费假设。
3. **V2-C Agent/团队**：项目/团队角色、预算、工作流审计、任务幂等、工具调用授权、资源配额和防循环成本；优先满足真实试点需求，不预造复杂编排器。

**V2 启动门槛**：V1 稳定、V1.5 指标和回退可用、试点用户有明确需求、成本与合规模型可核实，并有足够维护能力；否则只做研究与技术方案。

## 6. 运营与商业验证原则

- 首批明确一种主要客户（个人开发者/小团队）和一个清晰使用场景。
- 优先验证：请求成功率、p95 延迟、按真实供应商账单校对的每次成功请求成本、API 使用转化、试点留存和支持工时。
- 收入、利润必须有真实收费和供应商成本证据；内部 quota 不是营收，上游价格页面不是实际账单。
- 商业 KPI 可以在有样本后由所有者定阈值；现在不凭空设定生产 SLO 或收入目标。
- 兼顾上游升级、AGPLv3/附加条款、公开仓库的敏感信息、数据安全及供应商可转售/授权条件。
